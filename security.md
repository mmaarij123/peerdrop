# Security and privacy

## Transfer threat model

| Boundary | Controls |
| --- | --- |
| Invite disclosure and reuse | The link is a bearer credential. Share it privately. The receiver token is in the fragment and is removed from the address bar when signaling acknowledges the authenticated join. Tokens have 256 bits of randomness, are role-bound, and are stored as hashes server-side. The receiver slot can be claimed once. |
| Unsolicited or malformed files | The receiver sees the filename and size and explicitly accepts before the sender reads bytes. The receiver checks metadata, byte count, and any configured cap. Names render as text. Download names exclude path separators and reserved device names, and long names are shortened to fit common filesystem limits. Large transfers use browser-private temporary files and a bounded write window. The app releases partial buffers and requests deletion of temporary files on failure. |
| Signaling abuse | Both WebSocket routes check the origin. The control socket checks a role token on the first message. Authenticated participants receive separate PeerJS registration grants, and the server restricts forwarding to the paired peer. A shared transfer key binds the attempted DataConnection to the session. Per-IP and per-connection limits, frame caps, heartbeat, and deadlines bound abuse. The app applies `Cache-Control: no-store` and `Referrer-Policy: no-referrer`. Keep tokens, SDP, ICE, and filenames out of logs. |
| Relay abuse | TURN credentials are issued after both roles authenticate. The shared secret stays server-side. The VPS example limits allocations and blocks private, loopback, link-local, and multicast IPv4 peers. Review relay quotas and firewall policy on the VPS. |
| Public hosting | Serve HTTPS and WSS, trust forwarded addresses only from the reverse proxy, and keep the app listener and Redis internal. The proxy routes by owner node. Invite tokens are carried in the fragment and the first authenticated control message. The separate PeerJS registration token is in the upgrade query. The example Caddy logger removes the `token` query parameter from request URIs. Omit that query or redact the token wherever else access logging is enabled. Keep secrets out of version control and public assets. |

WebRTC provides transport security. Invite possession authorizes the role. It does not identify a person. The signaling service can observe connection metadata while forwarding it. TURN forwards encrypted packets and sees network endpoints and traffic volume. The configured TURN credentials expire about one minute after the active-session deadline. Ending an app session invalidates the invite immediately. An already issued TURN credential can remain valid until its own expiry.

Production loads the TURN shared secret from a mounted file. The coturn wrapper writes its config to a private tmpfs file. Caddy has no secret mount. If an external Redis deployment requires credentials, load its URL from a mounted file and use TLS when the connection crosses a network trust boundary. The Compose example keeps Redis on an internal network with no published port. The app rejects new creations and joins when the shared limit store is unavailable.

Standalone HTTP development explicitly allows `localhost` and `127.0.0.1` on the configured port. The optional local TURN relay listens on IPv4 loopback and permits relay traffic only to loopback peers. It receives an ephemeral secret through standard input and stops when the parent process exits. Production requires the configured HTTPS origin and uses its external relay configuration.

## Human review before merging or publishing

Keep the [Privacy Policy](dist/privacy.html) aligned with the deployed service. Before publication, confirm the operator's legal identity and privacy contact, the infrastructure providers and where they process data, and any logging or retention that differs from the app defaults. Confirm the legal basis for processing, available privacy rights, and any disclosures about international transfers that apply to that deployment. Review the [Terms of Service](dist/terms.html) for the intended audience and jurisdiction, including the contact for support, abuse, and copyright reports. [ICO guidance on privacy notices](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/individual-rights/individual-rights/right-to-be-informed/)

Get human review for authentication or authorization, payments, cryptography, or collection, processing, logging, or storage of personally identifiable information. Review the PeerJS credential lifecycle, forwarding restrictions, query redaction, origin checks, and relay settings before public rollout. Record the outcome in [decisions.md](decisions.md).
